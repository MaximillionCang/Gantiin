# Item assessment contract

Current context entry, PRD 2.1: Treasurer supplies only event name and description. validatePolicy creates stable EVENT-RELEVANCE/EVENT-UNRELATED guardrails and policy_input=event_description; it does not invent extra event facts or require manual category/rule editing. The actual description and approved references govern relevance. Decider instructions require an item-specific explanation of missing relevance/personal purpose/conflict for each rejection; Why rejected displays that model-returned reason in claim results. Existing historical explicit-rule policies remain readable. Fresh version/snapshot validation continues unchanged.

The decider is separate from OCR: ai/decider.mjs, prompts/decider.mjs and schemas/assessment.mjs. It uses the resolved decider model and shared Gemini key through LangChain structured JSON output, with no payment tools, credentials, remaining funds or recipient input. Receipt/event/approved-reference evidence is passed as data. Receipt-only requests supply no fabricated purpose; legacy saved context is passed only when actually present.

Input is a validated receipt, current configured versioned policy, and uniquely identified explicitly approved reference rows. Relevant rows are retrieved deterministically (word overlap, top 40); absence does not itself mean rejection. Current prohibitions win over history. Insufficient event evidence and unexplained product codes are rejected with specific English reasons; transport/schema/unavailable-data failures stay operational failures.

Output has policy_version and exactly one item result per receipt item: item_id, accepted/rejected decision, category, English reason, rule_ids, reference_ids and policy_version. Server validation checks coverage, unknown/duplicate IDs, known unique citations, allowance for acceptance, prohibition conflicts and policy version before allocation. Category matching is a conservative server guard; semantic application of natural-language rules still requires actual model evaluation. Tests do not establish semantic model accuracy.

Claims store exact policy/reference snapshots and digests, assessment time, extraction time and OCR/decider identities. Old persisted records remain readable. Current policy is rechecked before reserving funds; an in-flight payment keeps its immutable authorized snapshot. No model payment total is consumed. Job 5 consumes validated accepted IDs and deterministic net item amounts only.
